# CSE 121 hands-on lesson roadmap

**0.6.0: 35 top-level learning units, six modules, and 39 executable coding parts/files (30 console programs and nine robot programs).** Row 3 is a five-part group counted once in the course outline. This original tutoring sequence is aligned to [UW CSE 121, Spring 2026](https://courses.cs.washington.edu/courses/cse121/26sp/) and stays within introductory procedural Java.

The order follows `src/curriculum.js`, including declaration/debugging content from `src/lesson-content.js` and the three finish challenges from `src/challenges.js`. See [the verification records](RELEASING.md). Teacher readiness guidance is optional and does not gate software completion.

## Separate Lesson, Quiz, and coding pages

| Page | Student action | Transition |
|---|---|---|
| Lesson: `/learn/:lessonId` | Two slides: goal and concept plus interactive model. Optionally build, step, or manipulate the model here. | Enter coding at any time, or choose **Take quiz**. |
| Quiz: `/quiz/:lessonId` | Optionally answer the standalone prediction and read its feedback. | **Start practice**, **Start project**, or **Start assignment** is always available. |
| Practice: `/practice/:lessonId` | Ordinary coding tasks: edit native `Student.java`, use **Save & run**, inspect output/replay and checks; review notes are optional. | **Review the lesson** returns to Lesson voluntarily. Resuming existing code does not force review or quiz navigation. |
| Project: `/project/:lessonId` | The same coding workspace for the three robot challenges, listed at `/projects`. | Rows 33–35; each has its own Lesson and Quiz. |
| Assignment: `/assignment/:lessonId` | The same coding workspace for `autonomous-docking` and `java-final-report`, listed at `/assignments`. | Rows 31–32; each has its own Lesson and Quiz. |

Rows 1–30 are Practice units, including the five-part group at row 3. Rows 31–32 are Assignments and rows 33–35 are Projects. Catalogs do not add units. Legacy `/lesson/:lessonId` redirects to the appropriate coding route. **Save & run**, also available as **Pip: Save and Run Current Lesson** (`pip.runLesson`), explicitly saves the real Java file before compilation.

In the tables, **model actions belong to Lesson**, **predictions belong to the separate Quiz**, and **actual output, diagnostics, and replay checks belong to coding** (Practice, Project, or Assignment as mapped above). The final column offers optional teacher readiness guidance. All teaching sequences and review suggestions below are advisory.

## How to use this roadmap

- Prerequisites are teaching recommendations, not software locks. Follow the numbered path unless the student demonstrates the prerequisite independently.
- Have the student **manipulate → predict → code → run → explain**. Visual actions use the concept widget, actual output graphics, or 3D replay; any additional teacher-led variation is called out explicitly.
- Concept widgets illustrate ideas; they do not run the student's Java. Compare them with the result of **Save & run**.
- The test column combines implemented automated coverage with explicit teacher follow-ups. Never infer that every listed teaching variation is already automated.
- Progress schema 5 matches each lesson/part's current `assessmentVersion`: most are 2; `debug-semicolon` and `autonomous-docking` are 3. `practiceComplete` equals `hasPassedLesson`, which checks each group part against its own version. Only current code checks determine completion. Activity, Quiz, and review/reflection are optional, with no minimum text. Review notes are collapsed by default and autosave at any length. Saved reviews, quiz answers, and activities remain available without a data migration; older code passes may require new checks.
- Completed titles use strikethrough in module lists, catalogs, progress, completed modules, and completed part buttons, with visible **Completed** status.
- For every repair: reproduce the failure, name its cause, make the smallest justified edit, and rerun baseline plus changed cases. Use **Format Document** and review names, braces, indentation, and comments.

### Unit 3: five declaration-repair parts

The parent's `parts` array contains the following IDs in order, including itself. The four children have `parentId: 'debug-semicolon'`. Each part opens `/practice/<part-id>` and keeps its own file at `src/pip/lessons/<part_id>/Student.java` (hyphens become underscores in the directory name).

|---|---|---|
| 1. Missing semicolon — `debug-semicolon` | Add the missing `;` after `int bolts = 4`; preserve the variable print. | Compile, require the `int bolts` declaration and variable print, and pass changed initializer cases. Explain where the compiler reported versus where the error began. |
| 2. Unknown type — `debug-declaration-type` | Replace `integer` with `int`, keeping `bolts`, its initial value, and its print. | Reuse declaration checks and changed initializers. Explain why `integer` is not Java's whole-number primitive type. |
| 3. Redeclaration — `debug-redeclaration` | Keep the first declaration; remove the repeated type from `int parts = parts - used;` so it updates `parts`. | Require the variables and pass changed `parts`/`used` cases. Distinguish creating storage from replacing a value in the same scope. |
| 4. New variable — `debug-new-variable` | Declare `int remaining = parts - used;` and print `remaining`, preserving `parts` and `used`. | AST checks require all three typed variables, printing `remaining`, and no assignment, compound assignment, or unary update to `parts`/`used` in `main`; baseline and varied-input output cases also run. Teacher: explain why the new variable preserves the originals. |
| 5. Copied value — `debug-copy-value` | Keep `int backup = parts;`; after subtraction, print updated `parts` and original `backup`, rather than printing `parts` twice. | Baseline output is `7` then `12`; varied inputs must preserve the original value on the second line. Teacher: trace the copy before the update and contrast it with the later array-reference unit. |

The suggested teaching flow uses `/learn/debug-semicolon` and `/quiz/debug-semicolon`; the parent Quiz asks whether changing `parts` also changes `backup` after an `int` copy. The answer is no. Parent and child Lesson/Quiz views provide optional review. Part 1 uses assessment version 3; parts 2–5 each use version 2. All five passing completes the group; a pass for part 1 alone does not. Students may optionally record parent review notes explaining declaration versus assignment, redeclaration, and copying.

Initializer-based baseline cases run each original program without changing its source. Subsequent cases replace initializers only in temporary copies. This also applies to `java-types` and `debug-types`: replacing the required `0.5` with `0` fails the original-program baseline even if later varied cases would pass.

### Implemented challenge rules

These rules come from `Robot.java`, `Runner.java`, and `extension/runner.js`:

- **Coordinates and trials:** positions are in cm; heading zero points toward positive y. Every challenge uses starts (0, -120), (0, -70), and (0, -150); the last uses weaker motors (85 rather than 100 cm/s at full power). Physics runs at 60 Hz for 2,400 ticks, or 40 simulated seconds, unless a collision ends the trial early. **All three trials must pass.**
- **Obstacle and board:** the rectangle is 70 × 50 cm, centered at (0, 0) for detour/cargo and (0, 30) for hoop. Robot collision occurs when the center is less than 14 cm from the closest point on the rectangle. Board center limits are x from -196 to 196 and y from -166 to 166, inclusive; crossing a limit causes collision. Leave practical clearance rather than relying on exact contact boundaries. `distance()` senses the nearest obstacle or wall along the heading, with the robot radius subtracted.
- **Final stop:** every challenge fails on any robot collision or when `Math.abs(left) + Math.abs(right) > 0.001` at the end. The detour's radial goal tolerance is strictly less than 22 cm.
- **Cargo:** `collect()` loads cargo only within strictly less than 22 cm of (-100, 80), before delivery. `deliver()` requires cargo and distance strictly less than 22 cm from (100, 80); it clears carrying state and sets `wasDelivered()` true. The interaction methods do not require stopping or a particular heading, but teaching a stop at each station makes sequencing easier to inspect. Final stopping is graded.
- **Ball:** `collect()` loads the single ball within strictly less than 22 cm of (0, -70). `hasBall()` reports possession. Once collected, the ball cannot be replenished during that run; rerun for another attempt. `shoot(power)` validates a finite value from zero to one inclusive, consumes the loaded ball, and launches along the current heading. Without a loaded ball (or while a shot is active), a valid-power call does nothing.
- **Shot:** horizontal range is 300 × power cm. The fixed 1.5-second illustrative arc starts at 20 cm and reaches 30 cm at its endpoint; after completion, a scored ball stays at 30 cm and a miss is displayed at ground level. Scoring tests horizontal endpoint distance from (100, 120), at most 18 cm. There is no real ballistic solver or ball/obstacle collision check. Robot collision and final stopping still determine whether the trial passes.

The challenge briefings use the steering widget, not a waypoint editor or shot-power simulator. Route sketches, persistent-state tracing, power calculations, and comparisons of failed and successful runs remain teacher-led assessments. Reference navigation uses `Math.atan2`, `Math.hypot`, and heading normalization; introduce that supporting math explicitly if used, and assess the student's Java decomposition and feedback reasoning rather than memorization of the helper.

These are original simplified teaching challenges, not an official game clone. Only the docking assignment's mission 5 directly invokes `Student.dock`; all other robot labs and projects invoke `Student.update`.

## Teacher record and end-of-path review

For each lesson, record the date, help needed, failing case, successful changed case, explanation evidence, and the next revisit. A useful note is “needed a hint to move initialization outside the loop; independently traced the two-iteration retest,” rather than simply “passed.”

Before concluding this CSE 121 path, ask the student to write a fresh declaration, repair an unfamiliar small bug, trace a loop and array method, and plan one changed robot task. Revisit weak areas without the original hints. Review readable code, sensible tests, and reasoning alongside automated results. Local grading and completed activities are evidence of practice, not guaranteed cheat prevention or certification of course mastery.
